# GStreamer controlled-output findings

Date: 2026-09-09. Verdict: **the chosen composition is feasible for the exercised
Linux fixtures; it is not a production or audible-playback acceptance pass.**

The final recorded run passed 16 scenario checks and captured 144 PCM buffers
using GStreamer 1.28.2, Python GI, and a synchronized `fakesink`. No listener,
real Station, real music catalog, audio device, or macOS machine was involved.
Primary runtime evidence is [results.json](results.json), generated by
[probe.py](probe.py). Dependency inputs are recorded in `packages.sha256`.

## Observed

- A's output continued while a delayed candidate returned HTTP 503 and another
  candidate failed WAV decoding. The current session and its Queue remained A's.
  The largest observed interval between A's nominal 20 ms buffers was 24.946 ms;
  this is one run's measurement, not a scheduling guarantee.
- B completed decoding after C superseded it. B's commit was rejected and no B
  samples reached output. A second candidate was canceled after decoded data
  was ready; its samples also never reached output.
- Successful finite replacement preserved the opening marker and all 3,200
  frames of its 0.4-second fixture. Selection produced one commit; completion
  was recorded once after captured output drained, with the item retained.
- A true live source returned `NO_PREROLL` and produced usable data in PLAYING
  before selection. An endless local HTTP/WAV stream also reached output
  without a natural completion. These are different scheduling cases.
- Explicit stop ceased output after its bounded queued tail. A deliberately
  injected current-source error was attributed to that source; it also produced
  EOS, demonstrating that an EOS event must not erase an earlier error.
- A WAV response containing only 0.2 seconds of a declared 2-second recording
  produced EOS without an ERROR message. EOS alone cannot certify that a remote
  Track was complete.
- Output timestamps strictly increased. Each source's Python staging buffer
  peaked at 4,096 bytes; the GStreamer appsinks were configured with two-buffer
  and 65,536-byte limits, and output admitted at most two buffers at a time.
  Source shutdowns completed within 2.323 ms in this run.

The first exploratory run exposed a completion distinction: source EOS can
precede the last queued output samples. The captured final implementation waits
for the selected generation's output to drain. Only the final run's evidence
is retained here; the figures above refer to it.

## What this supports

Independent decoding plus one controller-owned output can enforce candidate
isolation and a serialized selection decision without relying on a backend's
ordinary replacement command. A failed candidate has no direct route to stop
the current pipeline. A generation check at selection prevents late candidate
audio; merely ignoring a stale UI callback would not provide this protection.

This supports taking the GStreamer composition back to the design interview.
It does not select GStreamer, approve a public Interface, or justify copying
this Python probe into the application.

## Still unproven

- Real output latency, audible continuity, device failure/recovery, macOS, Rust
  binding behavior, native packaging, and plugin discovery after installation.
- MP3/AAC/Opus/HLS, ICY metadata, HTTPS/TLS, real Station endpoints, and PLS/M3U
  resolution. Only the documented local WAV, generated PCM, and loopback HTTP
  fixtures were exercised.
- General buffering bounds for arbitrary decoded samples. The probe bounds
  queues but does not establish a universal maximum decoder buffer size.
- Long-duration clock drift, CPU use, changing channel layouts/sample rates,
  prolonged network stalls, pause/resume, live-edge freshness, and stress races.
  First-buffer readiness cannot promise that a stream will stay healthy.
- Real Songdial event handling, Queue advancement, error presentation, and the
  exact successful-commit observation. The dictionary and event log are only
  instruments for this experiment. Current-error versus normal-EOS policy must
  be resolved explicitly; the probe records both without a production policy.

No participant observations or usability verdict are claimed. Draft PR #22
and issue #11 were untouched. Stop here: broader work belongs to the resolved
design and fresh implementation tickets.
